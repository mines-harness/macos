# Mines device service

This service stores account membership and device public keys. It forwards short-lived signed WebRTC descriptions and optional generic push alerts. Conversations, catalog metadata, resources, and provider credentials travel over the approved device connection and never enter this service.

Accounts are self-hosted with Better Auth and Postgres. Configure `MINES_AUTH_URL` (the public HTTPS origin), `MINES_AUTH_SECRET` (at least 32 random characters), `MINES_ALLOWED_ORIGINS` (comma-separated client origins, including `mines://app` for the desktop app), and `DATABASE_URL`. Run `node infra/mines-control/src/main.ts` from the installed workspace. The process listens on loopback port 8788 by default; publish it behind HTTPS with the example Caddy configuration. Authentication tables migrate at startup. The public root page supports account creation, sign-in, and recovery. Do not enable access logs containing query strings: signaling connections and account emails contain short-lived credentials.

Configure `MINES_SMTP_HOST`, `MINES_SMTP_PORT`, and `MINES_SMTP_FROM`, with optional `MINES_SMTP_USER` and `MINES_SMTP_PASSWORD`, to send verification and password-reset emails through your own mail server. Email verification is required when SMTP is configured. Password recovery remains unavailable without SMTP. External SMTP requires TLS; a local mail service may accept unencrypted loopback connections. Password resets revoke existing account sessions.

Clients use `/api/auth/sign-up/email`, `/api/auth/sign-in/email`, `/api/auth/get-session`, and `/api/auth/sign-out`. Store the signed `set-auth-token` response header and send it as an Authorization bearer token; the unsigned JSON token is not accepted. Browser clients omit cookies for these requests. The reverse proxy must overwrite `X-Real-IP` with the actual client address because authentication rate limits use that header. Keep the service listener on loopback so clients cannot forge the trusted proxy header directly.

`compose.yaml` prepares a small single-instance deployment with Postgres and a STUN-only coturn service. Set `MINES_CONTROL_IMAGE` to a built workspace image and provide the required environment variables. Review and pin deployment images to registry digests before publishing. Only HTTPS and UDP 3478 need public ingress. No TURN ports, relay allocation, tunnel, or proxy for application traffic is configured. Device tickets and live presence are memory-local; run one control instance until presence coordination is deliberately added. Postgres needs encrypted backups and private networking.

The host must approve a device's key separately from account registration. Signed descriptions bind the approved identity to the DTLS certificate fingerprint; the signaling service cannot substitute a new transport certificate. Revoking account membership stops new signaling; revoke the device on the host as well to terminate established sessions. Protect the host's persisted identity as a credential.

Direct connectivity can fail on restrictive mobile or corporate networks and symmetric NAT. A failure must offer retry, another network, and cached history. It must never silently fall back to a relay. A sleeping or offline host cannot serve live history. Measure connection attempts and outcomes locally; export only opt-in aggregate counts by coarse failure category, without IPs, SDP, device identifiers, or chat content.

## Generic phone notifications

Set `MINES_EXPO_PUSH_ACCESS_TOKEN` only on the control service, from your own Expo account with enhanced push security enabled. Configure the mines EAS project (`MINES_EAS_PROJECT_ID`) and its APNs/FCM credentials, then build mobile with `MINES_CONTROL_URL`. Enable `MINES_PUSH_ENABLED=1` on a host already registered with that device service (for a boot service, put it in `<MINES_HOME>/service.env` and restart). On the phone, sign in and enable Agent updates in Notifications settings. No upstream T3 relay or push credentials are used. The capability stays disabled when the control service token is missing; APNs/FCM provisioning and an installed native build are still required for delivery.

The service accepts only signed fixed event kinds and random opaque IDs. It rejects extra fields such as chat titles, text, and thread IDs, and constructs the visible generic notification itself. Tokens register with account authentication plus the existing device key; only active devices in the same account receive events. Account/device limits bound requests, the host queue holds at most 64 generic events, and event IDs expire after one day. Push tokens expire after 90 days without registration refresh. Revoked devices cannot receive new alerts; explicit opt-out removes the token. Phones persist a pending removal when offline and retry it on the next session; revoking the device from another signed-in client stops alerts immediately at the service.

`accepted` means Expo accepted the request, never that a phone displayed it. The implementation drops notification failures rather than blocking agent execution and does not replay missed host events after a restart. No notification provider credentials are configured or deployed by this repository. Expo forwards these generic payloads to your configured APNs/FCM services; see [Expo push setup](https://docs.expo.dev/push-notifications/push-notifications-setup/) and [push security](https://docs.expo.dev/push-notifications/sending-notifications/#additional-security).
